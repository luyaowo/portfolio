## 引子：Claude Code 不只是终端里的代码聊天框

第一次打开 Claude Code，它很像一个装进终端的聊天框。但它还可以读取项目、执行操作、连接工具，并在多个界面中工作。

普通聊天通常是用户复制材料、获得建议，再自己完成后续操作。Claude Code 可以进入项目，直接读取和修改文件，运行命令和检查，再根据结果继续下一步。除了终端，它也能在 VS Code、JetBrains、桌面应用和浏览器中使用，这些界面连接的是同一套 Claude Code 引擎。[Claude Code 概述](https://code.claude.com/docs/zh-CN/overview)

本文以终端版作为主要演示。它的功能完整，Claude 读取了什么、修改了什么、运行了什么也更容易看清。文章从启动界面讲起，用一个写作任务串起规划、执行、纠正和验收的完整过程。

> 下文默认你已经安装 Claude Code 并完成登录。还没有安装时，可以先按照[官方 Quickstart](https://code.claude.com/docs/en/quickstart)完成准备。第一次进入某个文件夹，Claude Code 还可能询问是否信任这个工作区，确认文件夹来源和其中的配置没有问题后再继续。

## 第一章：打开 Claude Code 后，先看懂并会用

在准备处理的文件夹中打开终端，输入：

```bash
claude
```

启动后的界面比普通聊天多了一些信息。先确认 Claude 在哪里工作、当前使用什么模型、采用哪种权限模式，再开始交代任务。

### 先看懂四个区域

Claude Code 的版本和终端界面会继续变化，不必记住每项信息的固定位置。打开后主要看四个区域：

- **启动信息**，显示版本、模型和工作目录；
- **对话与行动区**，显示 Claude 的回复，以及读取文件、修改文件、运行命令的过程；
- **输入区**，可以输入自然语言、斜杠命令，也可以加入文件和图片；
- **状态区**，显示权限模式、任务状态和其他提示。

模型决定这次会话由哪个 Claude 处理，权限模式决定哪些行动要先征求同意。工作目录更需要每次确认，因为它决定 Claude 从哪个文件夹开始寻找和修改内容。

### 先确认 Claude 正在哪个文件夹里

工作目录可以理解为 Claude 当前打开的资料夹。启动信息中的路径就是它的位置。路径看不懂时，可以直接问：

```text
请告诉我当前工作目录是什么，里面有哪些主要文件。先不要修改。
```

目录不对时有两个命令可用：

| 命令 | 作用 |
|---|---|
| `/cd 路径` | 把当前会话切换到另一个项目，并读取新项目的 `CLAUDE.md` 说明 |
| `/add-dir 路径` | 让 Claude 可以访问另一个目录，但不切换当前项目 |

比如，正在处理网站项目，却发现工作目录还停在下载文件夹，就先用 `/cd` 切换。只有任务确实需要同时读取两个目录时，才用 `/add-dir`。后者增加的是访问范围，不会把另一个目录变成当前项目。

### 输入框可以放文字、文件和图片

输入内容后按 `Enter` 发送。需要换行时，可以使用 `Ctrl+J`。常见终端也支持 `Shift+Enter`，如果按下后仍然直接发送，可以运行一次 `/terminal-setup`。

| 操作 | 适合做什么 |
|---|---|
| 输入 `@` | 搜索并引用工作范围内的文件或文件夹 |
| 粘贴图片 | 把截图直接放进当前问题，常见快捷键是 `Ctrl+V` |

与其在输入框里描述“某个文件中间的那一段”，不如用 `@` 直接选中它。界面截图、报错截图也可以直接粘贴，让 Claude 对着实际内容判断。

整份文件或很长的日志更适合先保存成文件，再让 Claude 按路径读取，之后也更容易继续引用。

### 忘记操作时，从界面里查

Claude Code 的命令很多，不需要提前背下来。下面这些入口足够应付刚开始的查找和设置：

| 入口 | 能看到什么 |
|---|---|
| 输入 `/` | 当前真正可用的命令、Skills 和扩展，可继续输入文字筛选 |
| `/help` | 帮助和可用命令 |
| `/powerup` | 通过互动课程和动画演示了解 Claude Code 的常用能力 |
| `/status` | 版本、模型、账号和连接状态 |
| `/config` | 常用设置界面，包括主题、模型和输出偏好 |
| `/model` | 切换模型，并调整模型支持的思考强度 |
| `/effort` | 单独设置思考强度，使用 `auto` 恢复模型默认值 |
| `/usage` | 查看当前套餐的使用情况和限制 |
| `/doctor` | 检查安装、设置和扩展问题，确认后可以修复部分问题 |

不同平台、账号和安装内容看到的 `/` 菜单可能不同，以自己界面中实际出现的内容为准。`/config` 已经能完成大部分日常设置，不必刚开始就手动编辑配置文件。

输入 `/model` 会打开模型选择器。选定后，它会成为以后新会话的默认模型；如果只想切换当前会话，可以在选择器中的模型一行按 `s`。支持调节思考强度的模型，还可以在选择器中一并调整。也可以单独输入 `/effort`，从当前界面显示的可用档位中选择，输入 `/effort auto` 会恢复模型默认值。这里调整的是 Claude 在当前任务上投入的推理强度，不是在修改模型本身的参数或权重。

普通任务保持默认设置就够了。整合多份资料、规划较大改动或分析复杂问题时，可以提高思考强度；修改一句话、查找文件或执行明确操作时，没有必要每次调高。需要更换界面主题时，则使用 `/theme`。

### Claude 工作时，怎样看、怎样停

Claude 读取、修改或运行命令时，过程会显示在对话与行动区。方向不对时直接中断，不必等它完成整轮工作。

| 操作 | 作用 |
|---|---|
| `Esc` 或 `Ctrl+C` | 中断当前回复或操作；权限窗口打开时，`Esc` 会关闭窗口 |
| 连按两次 `Esc` | 输入框为空时打开 Rewind 菜单；有文字时清空草稿并保留在历史中 |
| `Ctrl+O` | 打开或关闭详细记录，查看工具调用和执行过程 |

中断不会撤销已经完成的修改或命令。快捷键也会随当前界面改变作用，需要帮助时可以使用 `/help`。尚未输入内容时按 `?`，可以打开快捷键帮助；输入框已有文字时，它只是普通字符。在全屏转录查看器中，按 `?` 也可以打开当前界面的快捷键帮助。

### 六种权限模式控制 Claude 可以直接做什么

权限模式决定 Claude 在编辑文件、运行命令或访问网络前，什么时候需要停下来询问。目前官方列出六种模式：

| 界面名称 | 普通使用时可以这样理解 | 适合的情况 |
|---|---|---|
| Manual（配置值为 `default`） | 直接读取通常不询问，其他行动一般先确认 | 第一次使用、陌生项目和敏感任务 |
| Accept Edits（`acceptEdits`） | 可以直接编辑项目内文件，并执行部分常见文件操作 | 任务范围清楚，准备在完成后统一检查修改 |
| Plan（`plan`） | 先读取、调查和提出计划，不修改源文件 | 需要先弄清项目或改动范围 |
| Auto（`auto`） | 常规操作减少询问，较高风险的操作由后台分类器判断 | 较长任务，希望少被确认窗口打断 |
| Don’t Ask（`dontAsk`） | 只执行预先允许的操作，其余直接拒绝 | 已经写好权限规则的受限环境 |
| Bypass Permissions（`bypassPermissions`） | 大部分操作直接执行，跳过常规确认 | 仅限与个人电脑隔离的容器或虚拟机 |

`Shift+Tab` 会在 Manual、Accept Edits、Plan 以及当前环境已启用的其他模式之间循环。Don’t Ask 不会出现在循环中，需要通过设置或启动参数启用。切换必须通过快捷键、界面选择器、启动参数或设置完成，只在聊天中说“进入 Plan”不会改变真实的权限模式。

> 这里的 `default` 是 Manual 的配置值，不代表它永远是新会话的默认启动模式。按照[官方权限模式说明](https://code.claude.com/docs/en/permission-modes)，从 2026 年 8 月 14 日起，Pro、Max 和 Team 计划的新会话会默认使用 Auto，用户或组织主动设置的默认值不受影响。实际使用时以状态区显示的模式为准。

刚开始使用时，Manual 便于逐项观察，Plan 适合先调查。Accept Edits 会少弹一些确认，但其中也包含部分文件操作，最好在已经知道怎样检查改动后再用。Auto 有后台检查，仍不等于所有操作都没有风险。Bypass Permissions 不适合作为减少点击的日常模式。

### `/permissions` 管理更具体的允许和拒绝

权限模式控制整体节奏，`/permissions` 用来管理具体规则：

- **Allow**，匹配的操作可以直接执行；
- **Ask**，每次匹配时都要确认；
- **Deny**，直接禁止匹配的操作。

多条规则同时匹配时，判断顺序是 Deny、Ask、Allow。

提示词和 `CLAUDE.md` 可以告诉 Claude 应该怎么做，却不能改变产品真正允许它做什么。密钥、私人资料和不希望 Claude 读取的文件，需要用 Deny 规则阻止。

## 第二章：把任务交代清楚，再决定是否先规划

接下来换一个更常见的任务：根据几份已有资料写一章文章。文件夹里已经有研究笔记、文章框架和旧草稿，但资料比较散，旧草稿又太长，还夹着一些不适合这篇文章的内容。

Claude Code 可以直接读取文件夹里的 Markdown、Word 导出的文字、访谈记录和参考资料，再把结果写回指定文档。用户要说清楚的是文章写给谁、要解决什么问题、哪些材料可信，以及什么内容不要写。

### 从看得见的问题开始

一句“帮我写篇文章”留下了很多没有决定的地方：主题有多大、写给谁、参考哪些资料、写多长、保存到哪里。更具体的说法是：

```text
请根据这个文件夹里的研究资料和文章框架，重写正文草稿的第一章。读者是第一次使用 Claude Code 的普通人，内容控制在约 2000 字，重点讲启动界面和基础操作。
```

这句话已经交代了材料所在的位置、目标读者、写作范围和大致篇幅。Anthropic 的官方提示词库也建议描述想要的结果，同时提供可以模仿或核对的材料。文件位置不确定时，可以让 Claude 自己在当前工作目录中查找；知道文件名时，直接用 `@` 引用会更准确。

文章任务常见的材料包括研究笔记、采访记录、旧稿、写作框架、参考文章和官方网页。没有确认过的事实不要让 Claude 自行补全，可以明确要求它标出缺少来源的内容，或者先停下来询问。

### 交代五件事就够了

任务信息可以按五件事检查，不必把它当成固定格式：

| 内容 | 需要说清什么 |
|---|---|
| 问题 | 现在发生了什么，在哪里可以看到 |
| 目标 | 希望最后变成什么样 |
| 材料 | 可以参考哪些文件、截图、网址或输出 |
| 边界 | 哪些内容不能修改，哪些行动不要进行 |
| 完成标准 | 根据什么判断任务已经完成 |

这次演示任务可以这样写：

```text
请先阅读 @研究结论.md、@文章框架.md 和 @正文草稿.md，不要立即修改文件。

问题：正文草稿的第一章太长，混入了开发者视角，还重复解释了上一篇文章已经讲过的 Agent 概念。

目标：重写第一章，让第一次使用 Claude Code 的普通读者看懂启动后的界面、工作目录、输入方式、常用设置和权限模式。

材料：研究结论负责提供事实，文章框架负责确定结构，正文草稿只作为已有表达的参考。涉及产品行为时，以研究结论中记录的官方资料为准。

边界：不要重复解释 Agent、Tool、Planning 和 Memory 的基础概念；不要假设读者懂代码或 Git；不要编造个人使用经历；不要修改第一章以外的正文。

完成标准：第一章控制在约 2000 字；覆盖框架列出的主要操作；产品事实能在研究资料中找到依据；只改正文草稿中的第一章；保留 Markdown 标题和参考链接。

先用普通语言复述你的理解，再说明准备保留和删除哪些内容、文章结构怎样安排、会参考哪些资料，以及完成后怎样检查。遇到需要我决定的地方先提问。
```

文章好不好仍然需要人来读，但不少检查可以提前写清楚。比如篇幅是否超出范围、要求的主题有没有遗漏、引用能否对应到资料、是否改动了其他章节、文档标题是否完整。只要求“写得好一点”，Claude 很难判断什么时候应该停下来。

### 让 Claude 只读相关资料

这次任务只涉及三份文件，不需要 Claude 把整个资料库都读一遍。范围太大时，旧版本、无关选题和重复资料都会进入对话，反而更难判断哪一份才是当前依据。

Claude 的第一次回复需要说明三份文件分别承担什么作用，旧草稿和新框架有哪些冲突，准备只修改哪一段，以及哪些事实仍然需要确认。研究资料负责事实，文章框架负责结构，旧草稿负责保留可用表达，这个优先关系也要说清楚。

Claude 仍然沿用旧草稿结构时，可以直接纠正：

```text
你仍然把旧草稿当成了结构依据。请以文章框架为准，研究结论只提供事实，旧草稿只保留仍然合适的表达。先重新整理第一章结构，不要修改文件。
```

这类纠正不需要重写整段任务。相关材料还在当前对话中，指出哪份资料的优先级错了即可。

### 哪些任务值得先进入 Plan Mode

改一个错别字、调整一句话或改一个明确的小标题，可以直接执行。下面几种写作任务更适合先规划：

| 任务情况 | 建议 |
|---|---|
| 修改位置明确，只改一两句话 | 可以直接执行 |
| 需要整合多份资料 | 先规划 |
| 要重写一整章或调整文章结构 | 先规划 |
| 新旧资料之间存在冲突 | 先规划 |
| 读者、重点或篇幅还没有决定 | 先让 Claude 提问，再规划 |

这个案例要对照三份材料并重写一整章，适合使用 Plan Mode。可以按 `Shift+Tab` 切换到 Plan，也可以直接输入：

```text
/plan 请阅读我引用的三份文件，先提出第一章的写作计划。计划中写明目标读者、章节结构、每部分使用的资料、准备删除的重复内容和完成后的检查方式。
```

在普通环境中，Plan Mode 允许 Claude 读取和搜索资料，但不会修改正文。它可以先把文章结构、资料关系和取舍理由摆出来，确认以后再动笔。Plan Mode 仍然不是沙箱，第一章提到的 Bypass Permissions 也会影响它能否作为可靠的编辑边界。

### 写作计划也需要审查

一份只有“阅读资料、重写文章、检查结果”三句话的计划仍然太模糊。审查时主要看四件事：目标读者和章节任务是否明确，三份资料的作用有没有混淆，修改范围是否越界，完成后的检查方法是否具体。没有资料支持的观点也要在执行前提出。

计划仍然把 Agent 基础概念放进第一章时，不要急着批准，可以继续回复：

```text
先不要执行。Agent 基础概念在上一篇已经讲过，请从计划中删除。第一章只保留启动界面、工作目录、输入、设置和权限操作，并补充每部分对应的官方资料来源。
```

计划较长时，按 `Ctrl+G` 可以在默认编辑器中打开并直接修改。Claude 给出最终计划后，界面会询问怎样继续。选择继续规划会留在 Plan Mode；选择批准则会退出 Plan Mode，并按照所选选项进入 Auto、Accept Edits 或逐项确认等执行方式。选项会随账号和环境变化，批准前看清它准备切换到哪种权限模式。

进入执行前，双方至少要对三件事有相同理解：文章写给谁，哪些材料可以作为依据，完成后按什么标准检查。

## 第三章：执行过程中，观察、纠正和授权

计划确认后，Claude 会开始读取资料、修改文档，有时还会运行搜索、统计或格式检查。这个阶段不需要一直盯着每个字，但也不适合把窗口放在一边等结果。行动记录会显示 Claude 正在接触哪些文件、准备做什么，以及什么时候需要用户同意。

### 从行动记录判断方向

执行开始后，界面里可能出现类似这样的记录，具体名称会随版本和所用工具变化：

```text
Read 研究结论.md
Read 文章框架.md
Search "Agent|Tool|Planning|Memory" in 正文草稿.md
Edit 正文草稿.md
```

行动记录要和计划对应起来。Claude 正在读的是否是约定的三份材料，搜索词是否围绕重复内容，编辑目标是否仍是正文草稿，修改范围有没有越过第一章。

默认界面隐藏了一部分细节，按 `Ctrl+O` 可以展开或收起详细记录。看到一条不认识的行动时，可以直接问：

```text
你刚才读取这个文件是为了确认什么？它会怎样影响第一章？先解释，不要继续修改。
```

解释仍要和任务边界对照。

### 写偏时先停下来

假设行动记录显示 Claude 已经开始修改正文草稿，但新内容又加入了大段 Agent 工作原理，还准备顺手调整第二章。这时继续等待只会增加后面的清理工作。按 `Esc` 或 `Ctrl+C` 中断当前行动，再指出具体偏差：

```text
先停止修改。新增内容又在解释 Agent 基础概念，修改范围也越过了第一章。请恢复第二章，只按 @文章框架.md 和 @研究结论.md 修正第一章。先说明准备怎样处理，不要立即编辑。
```

纠正时不必重发整段任务，只要说清楚哪里偏了、依据是哪份材料、接下来缩小到什么范围。如果是材料不足，可以补充新的文件或截图；如果是计划本身有问题，就让 Claude 回到 Plan Mode 重新整理。相同错误连续出现，往往说明当前对话里混入了互相冲突的要求，此时可以先整理已经确认的结论，再决定是否开一个新会话。

如果错误内容已经写进文件，也先停止后续行动，检查已经发生的修改后再决定修正还是回退。

### 权限请求要看它会影响什么

Claude Code 弹出权限请求时，先看行动、目标和范围是否与当前任务一致。下面这些情况足以覆盖一次普通文章任务：

| 权限请求 | 需要确认什么 |
|---|---|
| 修改正文草稿 | 文件路径是否正确，是否只改第一章 |
| 读取其他文件 | 是否真的与文章有关，会不会包含私人资料或密钥 |
| 运行搜索或篇幅统计 | 命令是只读取信息，还是还会改动文件 |
| 访问官方网页 | 域名是否可信，会向外发送哪些内容 |
| 安装新工具 | 当前任务是否真的需要，工具来自哪里 |
| 删除、覆盖或访问文件夹外的内容 | 目标是否明确，操作能否恢复，为什么不能在当前目录完成 |

第一次看到某项请求时，优先只批准这一次。确定同类操作长期都安全，才考虑以后自动允许。拒绝权限不会结束对话，可以让 Claude 换一种做法。比如，Claude 为了统计文章长度而要求安装一个新工具，这通常没有必要，可以回复：

```text
不要安装新工具。请使用当前环境已有的方式统计篇幅；如果仍然做不到，告诉我缺少什么，不要自行扩大操作范围。
```

长期允许的规则也需要定期检查。打开 `/permissions`，删除已经不再需要、范围过大或自己已经记不清用途的放行项。

终端命令看不懂时，先拒绝，再让 Claude 用普通语言说明命令的用途、为什么要运行、会读取或修改什么，以及结果保存在哪里。解释仍然含糊时，不要批准。

网络访问需要多看一步。只允许读取 Claude 官方文档时，应确认目标域名和发送内容，不要把包含个人资料的整份研究笔记一起交给外部服务。发布文章、发送消息、修改在线文档和写入数据库会影响本机之外的内容，也不能指望本地回退功能撤销。

### 权限和沙箱负责不同的边界

权限决定一项操作能不能开始，沙箱限制终端命令开始后可以接触哪些文件和网络。两者可以同时使用，但作用不同。

只读取和修改当前文件夹里的 Markdown 文档时，通常不必为了这一次任务临时研究复杂的沙箱配置。Claude 需要运行终端命令时，可以输入 `/sandbox` 查看沙箱是否开启、允许访问的范围，以及失败后是否可以请求转到沙箱外执行。

内置沙箱主要限制终端命令及其启动的其他程序，不会自动限制 Claude 的直接文件编辑、MCP 工具和 Hooks。某条命令在沙箱中失败后，Claude 可能申请到沙箱外重试，这是一项新的权限请求，需要重新判断原因和影响。

## 第四章：检查改动，用证据验收结果

Claude 回复“已完成”时，任务进入验收阶段。它的总结可以帮助定位结果，但文章是否写对，仍要看实际文件、检查结果和阅读感受。

### 先确认它到底改了什么

可以先让 Claude 停止编辑，只汇报当前结果：

```text
先不要继续修改。请列出这次改动涉及的文件和章节，说明删除了什么、保留了什么、增加了什么，并指出是否存在计划之外的变化。
```

这份汇报只能用来寻找检查入口，实际内容仍要回到文件里看。Diff 指的是修改前后对照，通常会把删除和新增内容用不同颜色标出来。Claude Code 在执行编辑时会显示修改片段，按 `Ctrl+O` 可以展开详细记录；桌面应用和 VS Code 扩展还提供更直观的差异视图。

当前版本可以输入 `/diff` 查看累计改动，也可以切换到 Claude 每轮产生的差异。桌面应用和 VS Code 扩展提供了更直观的差异视图。如果自己的 `/` 菜单中没有出现 `/diff`，再让 Claude 打开改动位置逐段说明，不需要为了查看文章改动先学习 Git。

检查差异时，先看文件名和章节范围。正文草稿之外有没有文件被改动，第二章是否仍然保持原样，第一章有没有整段意外删除，标题层级、代码块和参考链接是否出现大范围格式变化。大段改写最容易把原本正确的内容一起删掉，不能只看新增文字。

### 把完成标准变成可以检查的结果

文章质量有主观部分，也有一批结果可以直接核对。可以把第二章写下的完成标准一次交给 Claude：

```text
请对照第二章确定的完成标准验收第一章，先不要修改。

请汇报：
1. 实际修改了哪些文件和章节；
2. 篇幅和要求的主题是否符合约定；
3. 产品事实分别依据哪份资料或官方链接；
4. 是否改动了第一章以外的内容；
5. 哪些部分尚未验证或仍需要人工判断。

每项给出实际结果，不要只回复“已检查”或“没有问题”。
```

检查失败后，只修正失败项，再运行同一轮检查。篇幅、标题和关键词搜索只能证明文章满足了形式要求，内容是否自然、准确，仍然需要人来判断。

### 文章仍然要由人完整读一遍

打开修改后的第一章，从开头读到结尾。重点看普通读者能否跟上操作顺序，术语第一次出现时有没有解释，段落是否仍然偏向开发者，内容有没有和后面章节重复，引用能否支持旁边的事实。

遇到拿不准的产品描述，可以要求 Claude 回到来源：

```text
请为“Plan Mode 不修改源文件”这句话指出具体资料位置，并说明原文支持到什么程度。如果资料只能支持更有限的说法，请先给出修改建议，不要直接改稿。
```

这种问法会把事实、推断和修改建议分开。来源找不到时，删掉或收窄说法比让 Claude 凭印象补充更可靠。

重要文章还可以开一个新会话做独立审查。新会话没有参与前面的写作过程，更容易发现原会话已经习惯的结构和表达问题：

```text
请只审查，不修改。阅读 @正文草稿.md 的第一章，并根据 @文章框架.md 和 @研究结论.md 检查：是否适合第一次使用 Claude Code 的普通读者，是否遗漏必要操作，是否重复上一篇 Agent 文章，是否存在没有资料支持的产品描述。只报告具体问题和依据，不评价个人写作偏好。
```

小改动不必每次新开会话，长文、准备公开发布的内容或经过多轮重写的章节更值得增加一次独立检查。

### 写坏以后怎样回到之前的版本

每次发送用户提示前，Claude Code 都会创建 Checkpoint，记录当时的文件状态。连按两次 `Esc` 或输入 `/rewind` 可以打开回退菜单，并选择恢复对话、恢复文件、恢复两者，或从某条消息开始总结对话。

文章措辞写坏了，但前面的目标和资料判断仍然有用，可以只恢复文件；任务方向从一开始就理解错了，可以同时恢复对话和文件。只恢复对话会保留当前文件，因此选择前要看清菜单中准备恢复的对象和时间点。

> Checkpoint 不依赖 Git，关闭终端后恢复原会话时仍然可以使用，但它只覆盖当前会话中 Claude 直接进行的本地文件修改。终端命令、其他程序和大多数 Subagent 改动的文件不能通过当前会话的 Rewind 完整恢复，已经发送的消息、修改的在线文档、数据库写入和发布操作也无法通过 `/rewind` 撤销。

## 第五章：管理会话、上下文和项目知识

Claude Code 把一次对话保存为会话（Session）。会话中的聊天记录、文件内容和工具结果组成上下文（Context）。一篇文章从调研做到验收，上下文里已经积累了多轮要求、搜索结果和失败尝试。信息越来越多以后，可以先看里面装了什么，再决定继续、压缩还是重新开始。

### `/context` 显示当前会话装了什么

输入 `/context`，Claude Code 会按类别显示当前上下文的占用。里面有聊天记录、项目说明、`CLAUDE.md`、Auto Memory、扩展工具、读取过的文件、搜索结果和终端输出。

在文章任务中，几份长研究资料和多轮草稿通常比用户输入的几句话占用更多空间。反复让 Claude 读取整份旧稿、粘贴大段网页原文，或者保留已经放弃的写作方向，都会让后面的判断受到干扰。

文件和工具输出同样会占用空间。长日志不必全部回到对话里，可以直接要求：

```text
只返回检查结论、失败位置和必要证据，不要粘贴完整日志。
```

### 临时问题使用 `/btw`

想确认一个当前会话里的小问题，又不希望它进入聊天历史，可以使用 `/btw`：

```text
/btw 我们刚才确定的目标字数是多少？
```

`/btw` 能看到当前上下文，但不能读取新文件或运行命令。Claude 正在执行任务时也可以使用它，不会中断主任务。不带问题运行 `/btw`，可以重新打开最近的侧边问题并查看以前的回答。需要 Claude 调查新信息时，仍然使用普通对话。

### 同一任务太长时使用 `/compact`

如果目标没有变化，只是对话历史太长，可以在一个自然停顿处运行 `/compact`。它会用一份结构化摘要替换较早的对话，尽量保留目标、关键决定、相关文件、遇到的问题和未完成事项。

压缩前可以补充希望保留的内容：

```text
/compact 保留文章的目标读者、资料优先级、已经确认的章节结构、修改过的文件、尚未解决的问题和验收标准。删去失败草稿与重复讨论。
```

摘要不会保留每一个句子，需要精确引用时，Claude 可能重新读取文件。Claude Code 接近上下文上限时也会自动压缩；手动 `/compact` 可以选在一章完成之类的停顿处，并明确哪些信息要留下。每次都要遵守的规则更适合放进 `CLAUDE.md`。

只想压缩某一段对话时，可以打开 `/rewind` 菜单，在一个时间点选择“从此处总结”或“到此处总结”。前者压缩所选位置之后的内容，适合收起已经放弃的旁支讨论；后者压缩较早内容，保留最近工作的完整细节。它比 `/compact` 更有针对性，不会恢复或改动磁盘上的文件。

### 什么时候清空，什么时候恢复

| 当前情况 | 更合适的操作 |
|---|---|
| 仍是同一任务，只是历史太长 | `/compact` |
| 开始一个无关任务 | `/clear` 或新开会话 |
| 同一错误已经纠正多次，失败方向干扰判断 | 整理确认过的信息，再 `/clear` |
| 回到以前的任务 | `/resume` |
| 保留原会话，同时尝试另一种方向 | `/branch` |
| 以后需要快速找到当前任务 | `/rename` |

`/clear` 会以空上下文开始新的对话，之前的会话仍保存在本地，可以通过 `/resume` 找回。重新开始前，先把当前确认的目标、资料、边界和文件状态整理成一段新的开场提示，不要把整段旧对话再次粘贴回来。

`/branch` 会保留原会话，并复制当前对话尝试另一种文章结构。任务还没有结束时，可以用 `/rename claude-code-article` 取一个容易辨认的名字，隔天再通过 `/resume` 找回。恢复后先确认工作目录和文件状态，因为磁盘上的文档可能已经被其他工具修改过。

### 用 `CLAUDE.md` 保存每次都需要的规则

新会话不会带上旧会话的完整聊天记录。放在项目文件夹根目录的 `CLAUDE.md` 会在每次会话开始时读取，适合保存长期成立、每次都需要的项目说明。它就是普通的 Markdown 文件，不要求读者会编程。

这篇文章的文件夹可以使用一份很短的 `CLAUDE.md`：

```markdown
# 文章定位
- 读者是第一次使用 Claude Code 的普通人，不假设读者懂代码或 Git。
- 先讲具体操作，术语第一次出现时用普通语言解释。

# 资料和边界
- 涉及产品行为时，以 Claude Code 官方资料为准，并保留来源。
- 不编造个人经历或没有来源的事实，修改后保留标题、代码块和参考链接。

# 工作方式
- 修改前确认目标章节、参考资料、不能改动的内容和验收标准。
- 压缩时保留已经确认的决定、修改过的文件、检查结果和未完成事项，完整日志与失败草稿可以删除。
```

这里没有写“今天只改第一章”之类的临时要求，因为它们不会在每次会话中成立。整份研究资料和随时会变化的计划也不适合复制进来。文件越长、规则越含糊或彼此冲突，Claude 越容易漏掉其中一条。规则也会过时，隔一段时间要删除已经不成立或不再需要的内容。

项目很大时，可以用 `.claude/rules/` 让特定要求只在读取对应文件时加载。普通文章文件夹先用一份短 `CLAUDE.md` 就够了。

`CLAUDE.md` 是用户写给 Claude 的明确要求，Auto Memory 是 Claude 在工作中保存的模式、偏好和经验。输入 `/memory` 可以查看和编辑不同范围的记忆文件，也可以管理自动记忆。要确认当前会话实际加载了哪些文件，使用 `/context`。

这些内容会影响 Claude 的判断，却不能代替权限规则。密钥、私人资料和必须禁止的操作，应继续使用第三章介绍的 Deny 规则或其他强制限制。

### 写了规则却没有生效时怎么查

可以按四个入口逐步确认：

| 入口 | 先确认什么 |
|---|---|
| `/memory` | 记忆文件放在哪里，其中写了什么，Auto Memory 是否开启 |
| `/context` | 当前会话实际加载了哪些记忆文件，占用了多少空间 |
| `/status` | 当前加载了哪些用户、项目或组织设置 |
| `/doctor` | 设置文件、安装和扩展是否存在明显问题 |

会话中途修改 `CLAUDE.md` 后，可以运行 `/compact`、`/clear` 或重新启动，让新内容重新加载。文件已经加载，Claude 仍然没有遵守时，可以检查规则是否太长、含糊或互相冲突。需要每次必然执行的动作，应该交给权限或 Hooks。

## 第六章：进阶地图，遇到重复工作再扩展

前面的文章任务只依靠文件读取、搜索、编辑和会话管理就能完成。下面这些扩展能力不影响日常使用，可以等问题反复出现后再了解。增加前可以看三件事：它省掉了哪段重复工作，会接触哪些文件或账号，装好后怎样验证和停用。

### 根据重复出现的问题选择能力

| 反复出现的问题 | 更合适的能力 |
|---|---|
| Claude 总忘记固定的项目要求 | `CLAUDE.md` |
| 同一套说明和步骤反复粘贴 | Skill |
| 经常从另一个系统复制资料 | MCP |
| 某项检查必须在固定时机发生 | Hook |
| 调研会产生大量中间内容 | Subagent |
| 一整套扩展需要跨项目共享和升级 | Plugin |

Skill 和 MCP 会尽量按需加载，但调用后产生的内容仍会进入上下文。这些扩展也会增加权限和维护成本，问题没有重复出现时，继续直接交代任务更简单。

### 把文章发布前检查做成一个 Skill

第四章的验收提示会在每章完成和发布前重复出现，适合保存成 Skill。

项目 Skill 放在当前文件夹的 `.claude/skills/` 中，只对这个项目生效。可以直接让 Claude 创建，不需要手动输入终端命令：

```text
请为当前项目创建一个名为 article-final-check 的 Skill，保存到 .claude/skills/article-final-check/SKILL.md。

它只在我输入 /article-final-check 时运行。只审查，不修改文件或访问网络。检查目标读者、结构、资料依据、重复内容、篇幅、Markdown 完整性、私人信息和遗留占位符。

先展示准备写入的完整内容，等我确认后再创建。
```

让 Claude 先展示准备创建的内容，是为了检查 Skill 的触发方式、步骤、边界和输出是否符合预期。若只希望由用户主动调用，也要明确写进要求。完整的 `SKILL.md` 示例放在文末附录，需要自己创建时再查看。

创建后先输入 `/skills` 确认名称和来源，再用练习副本调用：

```text
/article-final-check @正文草稿.md @文章框架.md @研究结论.md
```

测试时可以故意留下一个 `TODO`，确认 Skill 能指出位置，同时检查文件没有被修改。从外部安装 Skill 时，要阅读 `SKILL.md` 和它引用的脚本，因为 Skill 也可以运行命令或申请工具权限。

### MCP、Hooks、Subagents 和 Plugins 分别放在哪里

经常从 Notion、Figma 或其他系统复制资料时，可以考虑 MCP。使用 `/mcp` 查看连接状态，添加前确认服务器来源、可访问的数据和权限。Claude Code 默认按需查找 MCP 工具，闲置连接对上下文的影响较小；MCP 返回的大段内容仍会占用上下文，不用的连接可以关闭。

某项动作必须在固定时机发生时，再考虑 Hook。输入 `/hooks` 可以查看当前加载的 Hook 配置。`PreToolUse` 可以在操作前阻止它，`PostToolUse` 发生在操作完成后，无法撤销结果。Hook 适合固定、可判断的规则，需要阅读大量资料和权衡的任务更适合 Skill 或 Subagent。Hook 会自动运行命令或调用外部服务，只使用能够读懂的配置。

大量资料会挤满主上下文时，可以让 Subagent 独立处理，最后只返回摘要。它的主要价值不一定是同时做更多事，而是把搜索结果、日志和中间材料留在独立上下文中。偶尔使用时，直接说“请用一个 Subagent 核对全部参考链接，只返回失效链接和证据”即可。

Plugin 适合把多种扩展打包并跨项目共享。输入 `/plugin` 可以打开管理界面，也可以通过它安装、启用、停用和查看 Plugin。安装前检查来源和内容，因为 Plugin 能以当前用户权限运行代码，属于高信任扩展。安装或更新后没有生效时，可以使用 `/reload-plugins` 重新加载当前会话；如果重新加载会改变 MCP 工具，界面可能要求确认或提示使用 `--force`。

扩展装好却没有出现时，可以依次查看 `/skills`、`/hooks`、`/mcp` 和 `/plugin`，确认对应组件是否已经加载。仍然无法判断时，再运行 `/doctor` 检查安装和配置错误。

### `/goal` 和 `/loop` 适合有明确停止条件的任务

`/goal` 为当前会话设置完成条件。每轮结束后，独立评估器根据对话中的证据决定是否继续。条件需要写明可测量的结果、证明方法、不能破坏的约束和最大回合。

文章质量主要依赖人工判断，不适合使用“把文章写到满意”为目标。它可以处理文章里的机械检查，比如：

```text
/goal 正文中不再有 TODO，所有 Markdown 链接都已经检查并在对话中报告结果，正文草稿之外的文件没有修改；满足条件或运行 10 轮后停止。
```

评估器不会自己读取文件或运行检查，只能判断对话中已有的结果。`/goal` 也不会改变权限模式，使用 `/goal clear` 可以提前停止。

`/loop` 用于隔一段时间重复检查，比如每隔五分钟查看长任务是否完成。它属于当前会话，电脑和 Claude Code 都要保持运行。

### 并行能力先看谁来协调

| 能力 | 谁协调 | 适合什么情况 |
|---|---|---|
| Subagent | 主 Claude | 独立辅助任务，只需要最后结果 |
| Agent View | 用户 | 多个互不依赖的完整后台任务 |
| Agent Teams | Claude 负责人 | 成员需要沟通并共享任务状态 |
| Dynamic Workflows | 脚本 | 大规模、可重复、带循环和交叉验证的任务 |

Dynamic Workflows 用脚本控制多批 Subagent 怎样启动、循环和交叉验证，适合大量资料、批量处理和需要多次核对的任务。截至 2026 年 8 月，官方仍将 Agent View 标为研究预览，将 Agent Teams 标为实验性功能。并行会增加 Token、权限请求和协调成本，几个任务会修改同一份文章时，顺序执行更稳妥。

部分新版本的 `/effort` 选择器还会显示 `ultracode`。它不只是更高一档的思考强度，而是把 `xhigh` 推理与自动工作流编排结合起来，适合需要 Claude 自己判断是否拆分和并行的复杂任务。日常工作继续使用普通思考档位即可。

### 看懂 Claude 正在调用什么工具

行动区中出现的 `Read`、`Edit` 和 `Bash` 不是需要用户输入的命令，而是 Claude 为完成任务调用的工具。看到这些名称时，可以用下面这张表判断它正在做什么。

| 工具名称 | Claude 正在做什么 |
|---|---|
| `Read` | 读取文件内容 |
| `Glob` | 按文件名或路径模式查找文件 |
| `Grep` | 在文件内容中搜索文字 |
| `Edit`、`Write` | 修改已有文件或创建新文件 |
| `Bash`、`PowerShell` | 在电脑上执行命令 |
| `WebSearch`、`WebFetch` | 搜索网络或读取网页 |
| `Agent` | 创建一个拥有独立上下文的 Subagent 处理任务 |
| `AskUserQuestion` | 暂停工作并向用户显示选择问题 |
| `Skill` | 调用一个已经安装的 Skill |
| `mcp__服务器__工具` | 调用 MCP 服务器提供的外部工具 |

实际显示的名称会随平台、版本和安装内容变化。工具是否需要确认，则由当前权限模式和权限规则决定。想查看更完整的调用过程时，可以按 `Ctrl+O` 打开详细记录。

### 常见术语

下面只解释本文中容易混淆的术语，需要深入了解时再查对应章节或官方文档。

| 术语 | 在 Claude Code 中的意思 |
|---|---|
| Session | 一次可以保存和恢复的会话，拥有独立的对话记录和上下文 |
| Context Window | Claude 当前能够使用的工作记忆，包括对话、文件内容、工具结果和已经加载的规则 |
| Compaction | 将较早的对话和工具结果压缩成摘要，为当前上下文释放空间 |
| Checkpoint | 每次用户提示前创建的恢复点，可以回退对话、Claude 直接进行的文件编辑或两者 |
| `CLAUDE.md` | 用户编写的长期说明，用来保存项目约定、重要背景和持续生效的规则 |
| Auto Memory | Claude 根据更正和偏好为自己记录的项目笔记 |
| Skill | 可重复使用的任务流程，可以包含说明、参考资料和脚本 |
| Hook | 在会话或工具调用的固定时机自动执行的处理程序 |
| MCP | 让 Claude Code 连接外部数据、工具和服务的开放协议 |
| Plugin | 可以安装和分享的扩展包，能够同时包含 Skills、Hooks、Subagents 和 MCP Servers 等组件 |
| Subagent | 在独立上下文中处理辅助任务，完成后把结果返回给主会话的 Claude 会话 |
| Permission Mode | 当前会话的整体批准方式，决定哪些操作需要先询问 |
| Sandbox | 限制终端命令可以访问哪些文件和网络的系统级边界，与权限提示是不同的控制层 |

### `article-final-check` Skill 完整示例

下面是第六章文章发布检查 Skill 的完整内容。它是进阶参考，不影响前面介绍的日常使用流程。

```markdown
---
name: article-final-check
description: 发布前审查中文 Markdown 文章，检查结构、来源、重复内容和文档完整性。
disable-model-invocation: true
---

# 任务

只审查用户引用的文章，不修改文件，不访问网络。

# 检查

1. 目标读者和章节目标是否一致。
2. 产品事实是否能在用户提供的研究资料中找到依据。
3. 是否重复已有章节，或出现没有解释的术语。
4. 篇幅、标题层级、代码块和 Markdown 链接是否完整。
5. 是否残留 TODO、配图占位、私人路径、账号或密钥。

# 输出

按影响列出问题，写明位置、依据和修改建议。无法确认的内容单独列出。
```
